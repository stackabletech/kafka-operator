= First steps
:description: Deploy a Kafka cluster in KRaft mode on Kubernetes with Stackable Operators, declare a topic with a KafkaTopic, and verify it by producing and consuming data.

After going through the xref:getting_started/installation.adoc[] section and having installed all the operators, you now deploy a Kafka cluster in xref:usage-guide/kraft-controller.adoc[KRaft mode] and declare a topic.
Afterward you can <<_verify_that_it_works, verify that it works>> by producing test data into the topic and consuming it.

== Setup

Kafka in KRaft mode manages its metadata itself, so no ZooKeeper is needed.
The cluster consists of two roles:

* The `controllers` store the cluster metadata and take part in the metadata quorum.
* The `brokers` serve the clients.

[source,bash]
----

----

This creates the actual Kafka instance.
The cluster has a single controller to keep the resource requirements low.
For production, use three or more (odd number of) controllers.

The `managementAccess` section makes the operator deploy an _agent_ next to the cluster.
The agent manages resources inside Kafka, such as topics, so that you can declare them in Kubernetes.
Here, the agent connects without a client certificate, which is possible because the cluster does not require client authentication.
Learn more in xref:usage-guide/management-access.adoc[].

Show the topic as the agent sees it:

[source,bash]
----
kubectl get kafkatopics.kafka.stackable.tech test-data-topic
----

The output should look somewhat like this:

----
NAME              TOPIC             CLUSTER        PARTITIONS   REPLICATION FACTOR   READY   SYNCED   REASON   AGE
test-data-topic   test-data-topic   simple-kafka   1            3                    True    True     Synced   30s
----

Learn more about topics in xref:usage-guide/topics.adoc[].

== Verify that it works

Next, use the Kafka client scripts to publish and consume data on the topic created by the agent.

The Kafka operator has created a service called `simple-kafka-broker-default-bootstrap`.
This service represents the endpoint clients should initially connect to in order to publish and consume data.
First, make sure that the service exists and it is healthy:

[source,bash]
----
kubectl describe svc simple-kafka-broker-default-bootstrap
----

The output should look somewhat like this:

----
Name:                     simple-kafka-broker-default-bootstrap
Namespace:                default
Labels:                   app.kubernetes.io/component=broker
                          app.kubernetes.io/instance=simple-kafka-broker-default-bootstrap
                          app.kubernetes.io/managed-by=listeners.stackable.tech_listener
                          app.kubernetes.io/name=listener
                          app.kubernetes.io/role-group=default
                          app.kubernetes.io/version=4.3.1-stackable0.0.0-dev
                          stackable.tech/vendor=Stackable
Annotations:              <none>
Selector:                 listener.stackable.tech/mnt.9555cbb6f38d4b0ca1771e6d83d28e27=simple-kafka-broker-default-bootstrap
Type:                     NodePort
IP Family Policy:         SingleStack
IP Families:              IPv4
IP:                       10.105.88.52
IPs:                      10.105.88.52
Port:                     kafka-tls  9093/TCP
TargetPort:               9093/TCP
NodePort:                 kafka-tls  32608/TCP
Endpoints:                10.244.4.22:9093,10.244.4.24:9093,10.244.4.23:9093
Session Affinity:         None
External Traffic Policy:  Local
Internal Traffic Policy:  Cluster
Events:                   <none>
----

The output shows that there are three endpoints serviced here.
They correspond to the three broker pods belonging to the Kafka cluster.

Use the Kafka performance producer script to send a couple of messages to the topic previously created.
The brokers use TLS, so the command uses the client configuration that the operator provides in the broker Pod and connects to the address of the broker listener:

[source,bash]
----
include::example$getting_started/getting_started.sh[tag=write-data]
----

The output should contain the following line:

----
5 records sent, 1.138434 records/sec (0.00 MB/sec), 83.40 ms avg latency, 395.00 ms max latency, 3 ms 50th, 395 ms 95th, 395 ms 99th, 395 ms 99.9th.
----

This confirms that there were five messages sent to the topic and it also displays performance timers.
We are not interested in any performance indicators but appreciate the fact that there were five unique messages that we consume later.

----

----

You successfully created a Kafka cluster in KRaft mode, declared a topic with a KafkaTopic, and produced and consumed data.
